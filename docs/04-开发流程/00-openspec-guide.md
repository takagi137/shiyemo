# OpenSpec 开发流程指南

> 本文档定义"失业么"项目中 AI 辅助开发的标准化流程。
> 核心理念：先想清楚，再写代码。Spec 是"人想清楚了"的书面证据。

---

## 流程总览

```
需求输入 → proposal.md → design.md → specs/*.md → tasks.md → 人工评审 → AI 编码 → BDD 验证
    │           │            │            │           │           │           │          │
   用户        人写         人写         人写        人写         人审        AI写       人审
  描述需求    What/Why      How        规格定义    任务拆分     Spec        实现代码    结果
```

### 核心原则

| 原则 | 说明 |
|------|------|
| 人在回路 | 每个阶段产出必须人工确认后才能进入下一阶段 |
| 契约先行 | 编码前先定义明确的验收标准（Spec） |
| 可验证 | 每个任务都有明确的验收条件 |
| 渐进细化 | 从意图到设计到规格，逐步细化 |

---

## 产出物清单

| 产出物 | 格式 | 对应阶段 | 存放位置 |
|--------|------|---------|---------|
| proposal.md | Markdown | 需求输入 | `specs/<功能名>/proposal.md` |
| design.md | Markdown | Design | `specs/<功能名>/design.md` |
| specs/*.md | Markdown (Given/When/Then) | Spec | `specs/<功能名>/specs/*.md` |
| tasks.md | Markdown (任务清单) | 实现计划 | `specs/<功能名>/tasks.md` |

## 阶段 1：proposal.md（What & Why）

### 内容要求

| 字段 | 必须/可选 | 说明 |
|------|----------|------|
| 变更标题 | 必须 | 一句话描述要做什么 |
| 背景说明 | 必须 | 为什么要做这个变更 |
| 目标用户 | 必须 | 谁会使用这个功能 |
| 核心功能 | 必须 | 必须实现的功能点 |
| 不做范围 | 推荐 | 明确不在本次范围内的功能 |
| 成功标准 | 必须 | 如何判断功能完成 |

### 模板

```markdown
# proposal：<变更标题>

## 背景
- 为什么需要这个变更？
- 当前存在什么问题？

## 目标用户
- 这个功能给谁用？

## 核心功能
1. 功能点 1：简要描述
2. 功能点 2：简要描述
3. ...

## 不做范围（明确延后）
- 功能 X：因为 xxx，延后到 Phase2
- 功能 Y：...

## 成功标准
- [ ] 标准 1：可验证的条件
- [ ] 标准 2：可验证的条件
- [ ] 用户能完成 xxx 操作
- [ ] 系统能承受 xxx 并发
```

### 示例：用户注册功能

```markdown
# proposal：用户注册功能

## 背景
- 当前用户无法创建账户，无法使用核心功能
- 需要支持手机号 + 验证码注册方式

## 目标用户
- 首次使用"失业么"的用户

## 核心功能
1. 用户输入手机号并获取验证码
2. 用户填写验证码 + 昵称 + 密码完成注册
3. 注册成功后自动登录并跳转首页

## 不做范围
- 邮箱注册：延后到 Phase2
- 第三方登录（微信/GitHub）：延后到 Phase2
- 邀请注册：延后到 Phase2

## 成功标准
- [ ] 用户能通过手机号完成注册
- [ ] 验证码 5 分钟内有效
- [ ] 同一手机号 60 秒内只能获取一次验证码
- [ ] 注册成功后自动跳转首页
```

## 阶段 2：design.md（How）

### 内容要求

| 字段 | 必须/可选 | 说明 |
|------|----------|------|
| 技术决策 | 必须 | 选择什么方案，为什么 |
| 模块边界 | 必须 | 涉及哪些模块，做什么改动 |
| 接口设计 | 推荐 | API 端点、输入输出 |
| 数据变更 | 推荐 | 是否需要新增/修改表结构 |
| 依赖关系 | 可选 | 依赖哪些外部服务或其他模块 |
| 风险点 | 可选 | 潜在的技术风险 |

### 模板

```markdown
# design：<变更标题>

## 技术决策
| 决策点 | 选择 | 理由 |
|--------|------|------|
| xxx | 方案 A | 理由... |

## 模块影响
| 模块 | 改动类型 | 改动说明 |
|------|---------|---------|
| user | 新增 | 新增注册 handler |
| user/repo | 新增 | 新增 Create 方法 |

## 接口设计
```
POST /api/v1/auth/register
请求：{ phone, code, nickname, password }
响应：{ token, user }
```

## 数据变更
| 操作 | 对象 | 说明 |
|------|------|------|
| 新增 | users 表 | 新增字段 xxx |

## 依赖
- 短信服务：xxx
- Redis：存储验证码

## 风险点
- 验证码服务的稳定性
- 手机号格式校验的边界情况
```

## 阶段 3：specs/*.md（Given/When/Then）

### 内容要求

每个 spec 文件定义**一个场景**，包含：

| 字段 | 必须/可选 | 说明 |
|------|----------|------|
| 场景标题 | 必须 | 清晰描述场景 |
| 前置条件 (Given) | 必须 | 系统初始状态 |
- 用户未登录的访客
- 用户手机号未注册
- 场景：
  - 请求 POST /api/v1/auth/register
- 验证码错误
- 响应状态码 400
- 返回错误信息
- 验证码正确
- 昵称已存在
- 响应状态码 400
- 提示"昵称已存在"
- 所有信息正确
- 响应 200
- 返回 token 和用户信息
- 用户已登录，可访问首页
| 操作 (When) | 必须 | 触发的动作 |
| 预期结果 (Then) | 必须 | 系统应产生的结果 |

### 模板

```markdown
# spec：<场景标题>

## 场景描述
简要描述这个场景代表什么

## 规格

### Given <前置条件>
- 系统处于 xxx 状态
- 数据库中存在 xxx

### When <操作>
- 用户执行 xxx
- 系统调用 xxx

### Then <预期结果>
- 响应状态码为 xxx
- 数据库中 xxx
- 系统返回 xxx
```

### 示例：注册场景

```markdown
# spec：用户注册 - 成功场景

## 场景描述
新用户使用手机号 + 验证码成功注册账户

## 规格

### Given 用户满足注册条件
- 用户未登录
- 手机号 13800138000 未被注册
- 验证码 123456 已发送且有效

### When 用户提交注册请求
- POST /api/v1/auth/register
- 请求体：{ "phone": "13800138000", "code": "123456", "nickname": "测试用户", "password": "a123456" }

### Then 注册成功
- 响应状态码 200
- 响应体包含 token（JWT 格式）
- 响应体包含 user 对象（id, phone, nickname）
- 数据库 users 表新增一条记录
- phone = 13800138000
- nickname = 测试用户
- password_hash 不等于明文密码
```

```markdown
# spec：用户注册 - 验证码错误

## 场景描述
用户输入错误的验证码

## 规格

### Given 验证码校验
- 用户未登录
- 手机号 13800138000 未被注册
- 验证码 999999 是错误的

### When 用户提交注册请求
- POST /api/v1/auth/register
- 请求体：{ "phone": "13800138000", "code": "999999", "nickname": "测试用户", "password": "a123456" }

### Then 注册失败
- 响应状态码 400
- 响应 message 包含"验证码错误"
- 数据库 users 表无新增记录
```

## 阶段 4：tasks.md（实现清单）

### 内容要求

| 字段 | 必须/可选 | 说明 |
|------|----------|------|
| Phase 分段 | 必须 | 按实现顺序分阶段 |
| 任务描述 | 必须 | 清晰的完成条件 |
| 依赖关系 | 推荐 | 任务之间的先后依赖 |
| 验收条件 | 必须 | 对应的 spec 文件 |

### 模板

```markdown
# tasks：<变更标题>

## Phase 1：数据层

- [ ] 任务 1.1：创建 xxx migration
  - 验收：`go run cmd/migrate/main.go up` 成功
  - Spec：无

- [ ] 任务 1.2：实现 repo 的 Create 方法
  - 验收：单元测试通过
  - Spec：spec-creation.md

## Phase 2：业务层

- [ ] 任务 2.1：实现 service 的 Register 方法
  - 验收：单元测试通过
  - Spec：spec-creation.md, spec-validation.md

## Phase 3：接口层

- [ ] 任务 3.1：实现 POST /api/v1/auth/register handler
  - 验收：BDD 场景全部通过
  - Spec：全部 spec 文件

## Phase 4：验证

- [ ] 任务 4.1：运行全部 BDD 场景
  - 验收：通过率 100%
  
- [ ] 任务 4.2：人工验收测试
  - 验收：可正常使用注册功能
```

## 如何在本项目中使用

### 启动一个新功能

1. **创建 spec 目录**
   ```
   specs/<功能名>/
   ├── proposal.md
   ├── design.md
   ├── specs/
   │   ├── 01-成功场景.feature.md
   │   ├── 02-错误场景.feature.md
   │   └── ...
   └── tasks.md
   ```

2. **按顺序写文档**
   - 先写 proposal.md（人写）
   - 再写 design.md（人写或 AI 辅助）
   - 再写 specs/*.md（AI 生成，人审核）
   - 最后写 tasks.md（AI 生成，人审核）

3. **人工评审通过后，按 tasks.md 逐个执行**

4. **每个任务完成后，验证对应 spec**

### 给 AI 的指令模板

```markdown
请根据 `specs/<功能名>/` 目录下的 OpenSpec 文档，完成 `tasks.md` 中 Phase N 的任务。

约束：
1. 只实现 tasks.md 中 Phase N 的任务，不要超出范围
2. 实现后运行对应 spec 的 BDD 验证
3. 验证通过后输出总结，等待人工确认
```

## 快速开始：第一个功能

第一次使用 OpenSpec，建议从最简单的功能开始：

**推荐第一个功能**：用户注册（或登录）

这是因为：
- 边界清晰（独立模块）
- 涉及完整流程（输入 → 处理 → 存储 → 响应）
- 有明确的验证场景
- 后续功能都依赖用户系统

让 AI 帮你生成第一个 Spec：

```markdown
我要实现用户注册功能，帮我按 OpenSpec 流程生成 proposal.md / design.md / specs / tasks.md。

约束：
1. 手机号 + 验证码注册
2. 注册后自动登录
3. 不包含邮箱注册和第三方登录
```
