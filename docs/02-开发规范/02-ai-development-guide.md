# AI 开发约束文档

> 本文档定义 AI 在本项目开发中必须遵循的准则和红线。
> 所有 AI 生成的代码必须符合本文档约束，不遵守的产出必须被拒绝。

---

## 🔴 红线（绝对禁止）

| # | 红线 | 违反后果 |
|---|------|---------|
| 1 | 不得引入 Java/Python 作为后端 | 架构决策不可违背 |
| 2 | 不得使用除 GORM 外的其他 ORM | 技术栈统一 |
| 3 | 不得在 Phase1（MVP）阶段拆分微服务 | 保持单体架构 |
| 4 | 不得在 MVP 阶段实现即时通讯 | 功能范围控制 |
| 5 | 不得在 MVP 阶段实现推荐算法 | 功能范围控制 |
| 6 | 不得在 MVP 阶段实现支付系统 | 功能范围控制 |
| 7 | 不得修改已有的数据库迁移文件，只允许新增 | 数据安全 |
| 8 | 不得在 handler 层写业务逻辑 | 分层规范 |
| 9 | 不得直接拼接 SQL 字符串 | 安全红线 |
| 10 | 不得提交未测试的代码到 main 分支 | 质量红线 |

## 📋 编码前三问（每次 AI 编码前必须回答）

> 引用自 agent-kit 核心原则模块。

在开始任何编码任务前，AI 必须先回答（或向用户确认）这三个问题：

| # | 问题 | 目的 | 本项目检查点 |
|---|------|------|-------------|
| 1 | 我要改什么、为什么改、改的边界在哪里？ | 确保需求理解到位 | 明确功能模块 + 涉及文件列表 |
| 2 | 能不能拆成更小的任务？ | 控制单次生成范围 | 单次任务不超过 3 个文件 |
| 3 | 每一步怎么验证结果？ | 确保可检查 | 至少有一个 BDD 场景可通过 |

## 🎯 范围控制原则

> 引用自 agent-kit 核心原则模块：小任务比大任务可靠，分步比一步到位安全。

### 单次任务约束

| 约束项 | 最大值 | 说明 |
|--------|--------|------|
| 单次修改文件数 | 3 个 | 超过则拆分任务 |
| 单个函数行数 | 50 行 | 超过则重构 |
| 单个文件行数 | 300 行 | 超过则拆模块 |
| 单次提交含文件数 | 5 个 | 超过则分批提交 |

### 执行模式

```
❌ 错误模式：
  "帮我实现用户系统，包括注册、登录、个人资料、头像上传"

✅ 正确模式：
  任务 1：创建 users 表迁移
  任务 2：实现注册 API（handler + service + repo）
  任务 3：实现登录 API
  任务 4：实现个人资料 API
  ...每完成一个，验证通过后再继续
```

## 🏗️ 架构约束

### 分层规范

本项目严格采用 **handler → service → repo** 三层分层：

```
internal/
├── user/
│   ├── handler.go    # HTTP 处理层：参数校验、调用 service、返回响应
│   ├── service.go    # 业务逻辑层：纯业务逻辑，不依赖 HTTP
│   ├── repo.go       # 数据访问层：数据库操作，不包含业务逻辑
│   └── model.go      # 数据模型：结构体定义
```

### 层职责边界

| 层 | 职责 | 禁止 |
|----|------|------|
| handler | 参数校验、调用 service、返回响应 | 写业务逻辑、直接操作数据库 |
| service | 业务逻辑、事务编排、调用 repo | 依赖 HTTP 框架、直接返回 HTTP 响应 |
| repo | 数据库 CRUD、查询封装 | 写业务规则、返回 HTTP 错误码 |

## 🔧 API 设计约束

### 统一响应格式

所有 API 返回统一 JSON 格式：

```json
{
  "code": 0,          // 0 = 成功，非 0 = 失败
  "message": "ok",    // 提示信息
  "data": {}          // 业务数据，失败时为 null
}
```

### 错误码约定

| 错误码范围 | 含义 | 示例 |
|-----------|------|------|
| 0 | 成功 | - |
| 40000-40099 | 参数错误 | 40001 = 缺少必填参数 |
| 40100-40199 | 认证错误 | 40101 = 未登录，40102 = Token 过期 |
| 40300-40399 | 权限错误 | 40301 = 无权限 |
| 40400-40499 | 资源不存在 | 40401 = 用户不存在 |
| 50000-50999 | 服务错误 | 50001 = 数据库错误 |

### 路由规范

```
GET    /api/v1/posts          # 列表
GET    /api/v1/posts/:id      # 详情
POST   /api/v1/posts          # 创建
PUT    /api/v1/posts/:id      # 更新
DELETE /api/v1/posts/:id      # 删除（软删除）
```

## 🗄️ 数据库约束

| 约束项 | 规则 |
|--------|------|
| 命名规范 | 表名小写下划线（user_posts），字段同理 |
| 时间字段 | 统一用 created_at / updated_at，TIMESTAMPTZ 类型 |
| 软删除 | 所有业务表加 deleted_at，NULL 表示未删除 |
| JSON 字段 | PostgreSQL 原生 JSONB 类型，不存 JSON 字符串 |
| 索引 | 单表索引不超过 5 个，组合索引字段不超过 3 个 |

## 📐 验证优先原则

### 验证三层架构

所有功能必须通过三层验证，**任何一层未通过都不得标记为完成**：

| 层级 | 名称 | 覆盖范围 | 工具 | 执行时机 |
|------|------|---------|------|----------|
| L1 | 单元测试 | 每个函数/方法 | `go test` + `testify` | 开发中（必须） |
| L2 | 集成测试 | API 端点 | `httptest` + 真实 DB | 开发后（必须） |
| L3 | 部署验证 | 完整流程 | curl + BDD 场景 | 部署后（必须） |

### 验证层次详解

#### L1 - 单元测试（Unit Tests）

**要求**：每个 `service.go` 必须有对应的 `service_test.go`

```
internal/
├── auth/
│   ├── service.go
│   ├── service_test.go  ← 必须
│   ├── repo.go
│   └── repo_test.go     ← 必须
```

**测试范围**：
- ✅ 业务逻辑函数（service 层）
- ✅ 数据访问函数（repo 层）
- ✅ 工具函数（jwt, password 等）
- ❌ handler 层（使用 L2 集成测试覆盖）

**覆盖率要求**：
- service 层：≥ 80%
- repo 层：≥ 70%
- 工具函数：100%

**测试用例要求**：
```go
// 每个函数至少 3 个测试用例
func TestAuthService_Register(t *testing.T) {
    // 1. 正常场景（happy path）
    t.Run("success", func(t *testing.T) { ... })
    
    // 2. 边界场景
    t.Run("duplicate_email", func(t *testing.T) { ... })
    
    // 3. 错误场景
    t.Run("invalid_password", func(t *testing.T) { ... })
}
```

#### L2 - 集成测试（Integration Tests）

**要求**：每个功能模块必须有 API 集成测试

**测试范围**：
- HTTP 请求/响应
- 数据库交互（使用测试数据库）
- 认证/授权

**测试文件位置**：
```
tests/
├── integration/
│   ├── auth_test.go
│   ├── post_test.go
│   └── ...
```

**测试用例要求**：
```go
func TestRegisterByEmail(t *testing.T) {
    // 1. 正常注册
    t.Run("success", func(t *testing.T) { ... })
    
    // 2. 邮箱已存在
    t.Run("duplicate_email", func(t *testing.T) { ... })
    
    // 3. 参数缺失
    t.Run("missing_fields", func(t *testing.T) { ... })
    
    // 4. 参数格式错误
    t.Run("invalid_email_format", func(t *testing.T) { ... })
}
```

#### L3 - 部署验证（Deployment Verification）

**要求**：部署后必须运行 BDD 场景验证

**验证内容**：
- 健康检查：`GET /health`
- 核心流程：按照 `specs/*.feature.md` 逐条验证
- 回归测试：确保已有功能未被破坏

**验证方式**：
```bash
# 1. 健康检查
curl http://server:8080/health

# 2. 执行 BDD 场景验证脚本
./scripts/verify-bdd.sh

# 3. 手动关键路径验证
./scripts/test-auth.sh
```

### 场景覆盖要求

| 优先级 | 场景类型 | 说明 |
|--------|---------|------|
| P0 | 正常流程 | 用户最常用的 happy path |
| P1 | 边界情况 | 空值、超长、特殊字符 |
| P1 | 错误处理 | 认证失败、权限不足、资源不存在 |
| P2 | 并发场景 | 同一资源被多人同时操作 |
| P2 | 性能场景 | 列表分页、搜索响应时间 |

### 验证检查清单

每个功能完成前，必须确认：

- [ ] L1：单元测试通过（`go test ./...`）
- [ ] L1：测试覆盖率达标（service ≥ 80%）
- [ ] L2：集成测试通过
- [ ] L3：部署到验证环境成功
- [ ] L3：BDD 场景全部通过
- [ ] L3：关键路径手动验证通过

## ⚠️ AI 常见错误模式（pitfalls）

> 本文档随着项目推进持续更新，记录 AI 容易犯的错误。

### 已知错误模式

| # | 错误模式 | 正确做法 |
|---|---------|---------|
| 1 | 在 handler 里写业务逻辑 | handler 只做参数校验和调用 service |
| 2 | 直接拼接 SQL | 使用 GORM 的参数化查询 |
| 3 | 一次生成太多代码 | 拆成小任务，每步验证 |
| 4 | 不写错误处理 | 每个函数都要处理 error |
| 5 | 用 fmt.Println 打日志 | 使用结构化日志库 |
| 6 | JSON 格式化输出 | 保持与原文件格式一致 |
| 7 | 忽略并发安全 | 写操作加锁或用事务 |
| 8 | 硬编码配置 | 使用配置文件或环境变量 |
| 9 | 复制粘贴代码 | 抽取公共函数/组件 |
| 10 | 不考虑分页 | 列表接口必须支持分页 |

## 📝 提交规范

### Git 提交信息格式

```
<type>(<scope>): <subject>

<body>

<footer>
```

### Type 类型

| Type | 说明 |
|------|------|
| feat | 新功能 |
| fix | Bug 修复 |
| docs | 文档变更 |
| style | 代码格式（不影响功能） |
| refactor | 重构（不改变功能） |
| test | 测试相关 |
| chore | 构建/工具相关 |

### 示例

```
feat(user): 实现用户注册接口

- 新增 CreateUser handler
- 新增注册验证逻辑
- 新增 users 表 migration

Closes #12
```
